# OpenWebUI Tool-Path Prompt Cache Stability Plan Handoff

## Goal

Explain and plan a minimal, testable fix for the observed behavior:

- plain chat keeps prompt cache relatively stable
- tool-using chats show large cache drops
- Codex-style multi-tool turns remain cache-stable

The working target is not "make tool results cacheable". The target is to preserve the exact-prefix invariant across native tool continuations whenever the request can be represented as an append-only continuation.

## Current Evidence

### Codex Reference Pattern

Current open-source Codex code shows three important properties:

- `prompt_cache_key` defaults to the thread id, so it is stable across turns unless explicitly overridden.
- Each sampling request is built from recorded history, and tool outputs are appended to history.
- Stateful / websocket incremental sending is guarded by:
  - same non-input request fields
  - same tools
  - same prompt cache key
  - current input being a strict extension of the previous input
  - only then sending `previous_response_id` plus the incremental delta

### Local OpenWebUI / Bifrost Findings

Relevant files:

- `tools/openwebui/functions/bifrostapi.py`
- `backend/open_webui/utils/middleware.py`
- `backend/open_webui/routers/openai.py`

Potential cache breakers in the current path:

- `bifrostapi.py` auto-generates `prompt_cache_key` from model, system text, tools, and attachments rather than a chat/thread-level key.
- middleware tool continuation rewrites/restores system and user messages while applying citation/RAG source context after tool results.
- stateful continuation currently forwards `previous_response_id` when available, but does not enforce a Codex-like strict-delta guard.
- `bifrostapi.py` trims `input` for `previous_response_id` by taking from the last user message or function outputs, rather than proving it is a strict append-only delta from the previous request.

## Proposed Modification Strategy

### Phase 0: Instrument Before Changing Behavior

Add a debug-only request-shape fingerprint for native tool continuation:

- model
- route mode
- prompt cache key
- tools hash
- instructions/system hash
- input item count
- input hash
- previous response id presence
- continuation mode: stateless replay, stateful delta, or stateful rejected
- cached token readback when available

This should be gated behind an existing debug flag or a new narrowly named flag, for example `cache_debug` / `CACHE_PREFIX_DEBUG`, and must not log raw prompt/tool result content.

### Phase 1: Stabilize GPT/OpenAI Prompt Cache Key

Change only GPT/OpenAI requests generated by `bifrostapi.py`.

Candidate behavior:

- preserve explicit caller-provided `prompt_cache_key`
- otherwise prefer a chat/thread/session stable key if metadata contains one:
  - `chat_id`
  - or conversation id / session id
  - fallback to the existing stable-prefix hash only if no durable chat/thread id exists
- keep non-GPT behavior unchanged
- keep Gemini cached-content lookup semantics separate; do not silently reuse this change for Gemini

Rationale:

Codex uses a thread-scoped key. The current Bifrost auto key changes when system/tool/attachment summaries change, which can be useful for safety but is too brittle for tool continuations.

### Phase 2: Add Codex-Style Continuation Guard

Before forwarding `previous_response_id`, prove the next request is safe for stateful delta:

- same model
- same route mode
- same prompt cache key
- same tools hash
- same instructions/system hash
- same relevant generation controls
- current full Responses input starts with previous full input plus provider output items
- computed delta is non-empty and consists only of new tool outputs / required continuation messages

If any check fails:

- do not send `previous_response_id`
- fall back to full stateless replay
- log a compact guard-reject reason under debug

This mirrors Codex's "incremental only when request properties match and input is a strict extension" rule.

### Phase 3: Stop Rewriting Stable Prefix During Tool Continuation

For native tool-loop continuations, avoid mutating the earlier system/user messages after the first model call.

The current citation/RAG source context rewrite should be reviewed carefully:

- if the tool result itself is already a `function_call_output`, prefer leaving source markers in the tool output or a new appended continuation item
- do not re-template the last user message during the same native tool loop unless stateful continuation is disabled
- if source context must be added for frontend display, keep that display metadata out of the model input prefix

This phase should be scoped after Phase 2 tests expose which rewrites are actually causing guard rejection.

## Test Plan

### Unit Tests: `tools/openwebui/functions/bifrostapi.py`

Extend `backend/open_webui/test/util/test_bifrostapi_pipe_function.py`.

Tests:

- explicit `prompt_cache_key` still wins
- GPT request with `metadata.chat_id` gets a stable thread/chat-scoped key
- changing user text does not change generated key
- tool schema changes do not change thread/chat-scoped key when chat id is present
- no chat id falls back to existing prefix-hash behavior
- non-GPT request still does not auto-generate GPT prompt cache key

### Unit Tests: Responses Delta Guard

Add focused tests around a helper extracted from `backend/open_webui/utils/middleware.py`.

Tests:

- exact append-only tool output continuation is accepted and returns a delta
- model change rejects stateful continuation
- prompt cache key change rejects stateful continuation
- tools hash change rejects stateful continuation
- system/instructions hash change rejects stateful continuation
- input rewrite that is not a strict extension rejects stateful continuation
- rejection falls back without `previous_response_id`

### Middleware Regression Tests

Extend or add tests near existing native tool continuation coverage.

Tests:

- first native tool call stores the full request fingerprint
- follow-up tool result uses `previous_response_id` only when guard passes
- citation/source rewrite does not mutate stable prefix when stateful continuation is active
- when source rewrite is required, middleware disables stateful continuation and sends full replay

### Router Payload Tests

Update `backend/open_webui/test/util/test_openai_router_responses_payload.py`.

Tests:

- `previous_response_id` forwarding remains supported
- full replay path does not accidentally trim input
- stateful delta path sends only computed delta

### Optional Live Verification

Only after local tests pass:

- enable debug instrumentation on live or staging for one GPT model
- run one plain chat and one tool chat with the same model
- compare per-upstream-call:
  - prompt cache key
  - tools hash
  - instructions hash
  - continuation mode
  - cached tokens
- expected outcome:
  - first tool call has same stable prefix as plain chat
  - tool continuation either uses accepted delta or explicitly logs guard fallback
  - no silent stateful continuation with mutated prefix

## Rollback

- Phase 0 instrumentation can be disabled by config.
- Phase 1 can be reverted by preserving explicit `prompt_cache_key` and restoring prefix-hash fallback.
- Phase 2 is fail-closed: guard rejection falls back to current full replay.
- Phase 3 should be merged only after tests show no citation/source regression.
